# Job search workspace

`<repo>` = the folder this project is cloned into (the parent of this `JobSearch\` folder). Paths below are relative to this folder.

Layout:
- `JobSearch\` - this folder (Claude's working directory): `CLAUDE.md`, `applog.py`.
- `..\private\` - **all of the user's real data, gitignored**: `.env`, `job-search-config.json`, `resume.json`, the resume PDF, `applications.json`, `applications-archive.md`. A fresh clone has an empty `private\` (only `.gitkeep`, the folder's placeholder; everything else in it is gitignored): copy the files from `..\examples\` (drop `.example` from the names) and fill them in - see `..\README.md`.
- `..\examples\` - public templates of every file in `private\` (`.env.example`, `job-search-config.example.json`, `resume.example.json`, `Resume.example.pdf`, `applications.example.json`, `applications-archive.example.md`). Never put real data, names or personal details here. `job-search-config.example.json` is a generic template, not a copy: sample / `<placeholder>` values for roles, seniority, locations, skip rules, sources; blank `profile`; generic standingRules; the same autoApplyLoop step numbers with the workflow logic only (no names, dates, cities, companies or personal rules). When a workflow step or config field is added or changed in the real config, add the generic version there; when a new `.env` key is added, add it with an empty value to `examples\.env.example`.
- `..\launcher\` (StartJobSearch.exe source), `..\claude-browser-bridge\` (browser MCP server + Chrome extension).
- The repo is public: no names, personal paths (`C:\Users\<username>\...`) or private values in any committed file. Before any git commit / push, show the user the exact file list and wait for their OK.

Files:
- `..\private\job-search-config.json` - loaded by `StartJobSearch.exe`; search requirements and workflow (keep it valid JSON when editing):
  - search requirements: `roles`, `seniority`, `experienceYears`, `postedWithinHours`, `locations`, `minSalary`, `salaryExpectation` (expected yearly pay per location - the "Pay below your salary expectation" filter), `skip`, `sources`, `loop` (LinkedIn pacing), `jobFeed` (job APIs), `jobBoard` (job board: fetch interval, apply queue, watcher), `launcher` settings. Source of truth for WHAT to search; they win over anything conflicting in `profile` / `standingRules`.
  - `profile` - the user's own preference notes; `standingRules` - standing search rules.
  - `autoApplyLoop` - the step-by-step "program" Claude follows (job feed, apply queue, queue runs, forms, logins). New workflow rules from the user go into its `steps`.
- `..\private\applications.json` - log of every submitted / skipped / needs-approval / needs-user / pending / candidate job (older markdown log, if any: `..\private\applications-archive.md`). Use `applog.py`, don't hand-edit:
  - `python applog.py check "<company>" "<role>" [--id <job id>]` before analyzing any job - exit 0 = already logged, skip it.
  - `python applog.py add --company .. --role .. --location .. --status .. --url <job link> [--notes ..] [--id ..]` after each job (updates the existing entry for the same company+role / id). Always record the job link (autoApplyLoop step 1b): the company posting / application page for Submitted (required - applog refuses without it), else the LinkedIn post. `python applog.py list --no-link` shows entries missing a link.
  - `python applog.py open` lists jobs still waiting on the user / approval; `python applog.py note "<text>"` adds a note (e.g. a queue run summary).
  - `python applog.py answer --section <section> --question "<q>" --answer "<a>"` saves a question the user just answered into the ANSWER_* bank in `..\private\.env` (+ empty key in `..\examples\.env.example`); run it right after every new answer (autoApplyLoop step 6d).
- Job search source = Claude's own searches in Chrome (autoApplyLoop step 2g): the job board's **Search Google Jobs** / **Search LinkedIn** buttons save a search request (`..\private\job-board.json`); the watcher prints `search request <id>: google|linkedin`; Claude marks it running (`python jobboard.py search <id> running --note "<query> in all locations"`), searches in a new Chrome tab across EVERY preferred location (each `locations` area + Remote US), busiest first per `browserSearch.locationActivity` (updated after every search), looks only at jobs posted in the last `browserSearch.postedWithinHours` (24) hours, newest first, and keeps the ones that pass the search requirements (at most `browserSearch.candidatesPerSearch` (10) - a cap, not a target: no widening just to reach 10), writes them to a JSON file (company, title, location, workMode, salary, posted, url, applyUrl, description = the posting's required + preferred qualifications copied word for word (not a summary; the match score reads it), and companySize only when a page already opened shows it) and adds them with `python jobboard.py add <file.json> --search <id>` (marks the request done; `python jobboard.py search <id> failed --note ..` when blocked). Candidates are NOT logged in applications.json - the user approves them on the board. `python jobboard.py searches [--all]` lists requests. No SerpApi searches are used. The board's **Search company sites** button needs no Claude either: the board server (`companyjobs.py`) asks every company in `companyJobs.companies` (~140 large employers - Fortune 500 Workday career sites, big tech on Greenhouse / Lever / Ashby, DC contractors, plus Amazon, Microsoft and JPMorgan's Oracle site - each with an approximate `employees` size bucket; only companies bigger than `companyJobs.minEmployees` are searched: 10000 = the user's "large company" (10,001+); the board's **Company size** dropdown filters every job with a known `companySize` the same way; `ats` = workday / greenhouse / lever / ashby / oracle / amazon / microsoft) for each of `companyJobs.queries` through the sites' public job APIs, keeps software-type titles (`companyJobs.titleInclude`) posted in the last `companyJobs.postedWithinHours` (72) that pass `jobfilters.py` and are not on the board, reads each posting from the same site (qualifications, so the match score works), checks the filters again and adds up to `maxJobs` (25), at most `maxPerCompany` (3) per company, newest first; each job links to the company's own posting. `python companyjobs.py [--dry-run | --check]` (`--check` tests every company entry). **Growing the list (no tokens):** `python companyjobs.py --discover "Company A" "Company B" [--employees 10,001+] [--write]` finds each company's Greenhouse / Lever / Ashby / Workday board (Workday: finds the tenant's server - right server + wrong site answers 404 - then tries common site names, preferring one that lists jobs) and reports its job count and how many match the role queries; `--discover-file ../examples/large-companies.txt` (a seed list of ~270 large US employers: `Name | board/tenant names | employees`); `--add "<job link>" --name "Company" [--write]` adds one from any of its job links (Workday, Greenhouse, Lever, Ashby, Oracle). Without `--write` it only previews. **Any career, not only software:** the role lives in the config - `companyJobs.queries` (what each site is searched for) and `companyJobs.titleInclude` (regex every kept title must match); for e.g. banking change those two (and `jobFeed.titleInclude`, which every source uses). The board's **Search SimplifyJobs** button needs no Claude: the board server itself (`simplifyjobs.py`) downloads the SimplifyJobs new-grad list (github.com/SimplifyJobs/New-Grad-Positions, `listings.json`), keeps active software / data / AI jobs that pass `jobfilters.py` and are not on the board yet (widening 12h -> 24h -> 3 days -> 1 week until `browserSearch.candidatesPerSearch`), reads each kept job's simplify.jobs page for its requirements, preferred / desired qualifications, description and company size (the list itself has no job text), checks the filters again and adds them as candidates; `python simplifyjobs.py [--dry-run]` does the same from the command line. The board's **Search Simplify website** button also needs no Claude: it opens a dialog for the simplify.jobs page's `X-TYPESENSE-API-KEY` request header (the value, the header line or the whole copied header block; saved as `SIMPLIFY_TYPESENSE_KEY` in `..\private\.env`; blank = reuse) and the search options (posted within, locations, experience level (Simplify's tags; default Entry Level/New Grad + Junior), work mode, minimum salary, role searches, max jobs, search filters on/off), then the server (`simplifysite.py`) queries the site's search API (`browserSearch.simplifySite`: default queries, field names, software job categories `functions`, default window `postedWithinHours` (1 week)) - each click fetches the next `batchSize` (250) different jobs, newest first, older than the last click, never older than the posted-within window; when the window is used up the next click starts again from the newest - and adds the ones that match those options and pass `jobfilters.py` (no widening); the search API has no job text, so each kept job's simplify.jobs page is read for its requirements / responsibilities / description (years required, clearance) and company size before the filters are checked again; the qualifications always come from the company's own posting when it can be read (Simplify's rewritten requirement lists are not accurate): its click-through link is followed and the posting is read from the ATS's public API (Lever, Greenhouse, Ashby, Workable, Workday, Microsoft - `simplifysite.ats_text`), else the page's JobPosting JSON-LD, else its visible text, and saved as the job's applyUrl (`simplifysite.original_posting`); only when that posting is closed / unreadable / shows no qualification headings are Simplify's lists used (`qualsFrom` = `company posting` | `Simplify` on the job). Simplify jobs already on the board: `python simplifysite.py --refresh` re-reads them all (also used by `simplifyjobs.py`); a rejected key shows as a failed search - paste a fresh one. `python simplifysite.py [--dry-run | --raw]` from the command line (`--raw` prints one result document to check the field names). `python jobfeed.py` (SerpApi Google Jobs, `jobFeed` section, key `SERPAPI_API_KEY`, monthly budget `jobFeed.serpapi.monthlyRequestBudget`) is a manual tool only - run it only when the user asks; its jobs go on the board too (`--plan`, `--search N`, `--rejected`, `--hours N`).
- LinkedIn = the Search LinkedIn button, or when the user asks in chat (autoApplyLoop steps 2g / 2b): same steps, one results page at a time, paced per `loop.linkedinSearchDelayMinutes`, stop on HTTP 429.
- Job board = `python jobboard.py` (autoApplyLoop step 2s): a local page (`http://127.0.0.1:<jobBoard.port>`, default 8766; `jobboard.html`) listing the candidates Claude found (`..\private\job-board.json`) with salary, experience and work mode. The user approves jobs by putting them in the apply queue (in order) or skips them; with `jobBoard.requireSelection` (default true) Claude applies ONLY to queued jobs. Queued jobs are applied to with a QUEUE RUN (step 2q: one new Chrome tab per job, sign-in via the `wait_for_password` hand-off, blocked jobs logged as Needs User with their tab left open and Claude moving straight on to the next job) started by the queue watcher (see Starting the session) - there are no other apply rounds. `python jobboard.py queue` = the queue in order (exit 1 if empty; `--quiet` = one line for the watcher), `python jobboard.py applying <key>` = mark the job being applied to now; the page shows each job's applications.json status, so log every queued job with `--id <job id>` as usual. Skipped jobs are never applied to (and not offered again). The To review tab's **Remove all** button (two clicks) deletes the jobs it shows from the board; their keys are kept in `job-board.json` `removed` so later searches don't add them again. Jobs under "Waiting on you" (Needs User / Needs approval / Pending / Candidate) have **Continue application** (Needs User: puts the job back at the END of the apply queue, no page is opened - `python jobboard.py queue` marks it CONTINUE, finish it where it stopped), **Mark as submitted** (the user finished it themselves -> Submitted), **Skip** (-> Skipped) and, for Needs approval / Pending / Candidate, **Approve & apply** (-> status Approved and back in the apply queue; `python jobboard.py queue` marks it APPROVED BY THE USER - apply even though it failed a rule). The page has Location (the `locations` areas, Any location, Other) and Salary (Any salary, Salary listed, $50K+ ... $200K+) dropdowns and a "Hide jobs that fail a filter" checkbox per search filter - the filters (jobFeed regexes, `experienceYears`, `salaryExpectation`, `skip.rules`, `jobFeed.staffingAgencies`) live in `jobfilters.py`, shared with `jobfeed.py`; each card lists the filters it fails. Each card has a **Clearance** box (`jobinfo.clearance_from`, sentence by sentence): red "Active … required" = the posting wants a clearance the applicant already holds (active / current / at the time of application / required for start) - this is what the "Active clearance required" filter skips; amber "able to obtain" / "Public Trust" = can be granted after hire (OK to apply); "Mentions a clearance" = check the posting; hover shows the sentence. Each card also shows a **keyword match score** (e.g. "78% · 7/9" = 7 of the 9 tech keywords in the post's title + required + desired / preferred qualifications are on your resume - only the posting's Minimum / Required and Preferred Qualifications sections count (`matchscore.split_text` / `qual_sections`); responsibilities, the company blurb, benefits and Simplify skill tags the qualifications don't name are ignored; Strong 80+ / Good 65+ / Fair 50+ / Low; "no keywords" when the text names none) with the keywords you have and a Missing list (each missing keyword with a short explanation, its other names, "you have X - similar" when a close skill is on the resume, and a "required" tag - `glossary.py`): `matchscore.py`, plain keyword rules over `..\private\resume.json` - no AI, no tokens: ~200 hand-written tech keywords with careful patterns (`matchscore.VOCAB`, first layer), plus the **skill bank** (`skillbank.py`, `cache\skillbank.json`, gitignored: ~4,000 tools / languages / platforms with their other names from O*NET Technology Skills (onetcenter.org, CC BY 4.0) and Stack Overflow tags + tag synonyms (CC BY-SA), plus every skill name Simplify tags, learned as jobs come in), plus every item of the resume's skills lists - so a keyword counts however the post words it ("Postgres" / "PostgreSQL", "k8s" / "Kubernetes"). Bank rules: words postings write in plain lower case (ordinary English) are not skills, abbreviations count only in capitals, the hiring company's own name doesn't count. The board server builds the bank in the background when it is missing or a month old (`python skillbank.py build [--download]`; `find "<text>"`, `stats`). Experience, level, location and pay are not part of the score (the user judges those). `python matchscore.py` lists all scores, `--profile` the keywords read from the resume. The page can sort by **Best match + newest** (default: Strong / Good / Fair / Low match band, newest first inside each band), **Newest posted** or **Best match**, shows post times rounded to the nearest hour, fits one page of job cards in the window without scrolling (1-2 columns x 1-2 rows, max 4, chosen from the window size; each card at least 420 x 340 px, its keyword part scrolls inside the card), and hide jobs below a **minimum match**. They apply to the To review tab only (queued, waiting and finished jobs are always shown). These choices are saved in the browser only; Claude still applies to exactly what is in the queue. **Update my answers** (autoApplyLoop step 2u): the user uploads a resume (`..\private\uploads\`; the watcher prints `profile request <id>: new resume <path>` -> read it, update `resume.json`, fill answers with `python answerbank.py set KEY "value"`, then `python jobboard.py profile done --note ..`) and fills in the rest of the questions on a form (`answerbank.py`: APPLICANT_* / ANSWER_* values plus common questions not in the bank; `python answerbank.py missing` lists blanks; secrets are never shown). `StartJobSearch.exe` starts the page (`jobBoard.openOnStart`).
- Resume: the PDF in `..\private\` (exact path in autoApplyLoop step 4) is the file to upload; `..\private\resume.json` is the same resume as structured data (jobs, bullets, dates, education, skills) used to fill experience / Role Description fields (autoApplyLoop step 4a). Update both together. **Tailored resume per job** (`tailor.py`, config `resumeTailor`, autoApplyLoop step 4b): the master LaTeX resume (`resumeTailor.masterTex` in `..\private\`) is never changed for one job. On a job card, the user clicks a missing keyword to mark it as "I have this" for that job only (`addedSkills` in `job-board.json`; it counts in the score and shows as a green "+ keyword"; click again to remove it). When that job is in the apply queue, the board server copies the master `.tex`, adds those keywords to the matching Technical Skills line plus each keyword's saved placement (`..\private\keyword-placements.json`: Claude rewords ONE existing bullet that truthfully covers the keyword, or keeps it on the Skills line only when the experience doesn't show it - `python tailor.py place ...`, step 4b; the queue lists keywords still to place under PLACE FIRST), and compiles the copy with pdfLaTeX (MiKTeX) to `..\private\resumes\<job>\<pdfName>`. The card shows the build status, and `python jobboard.py queue` prints the `resume:` PDF to upload for each job (the master PDF when no keywords were added). `python tailor.py <key>` rebuilds one job's resume; `python tailor.py --check` shows the compiler and master files.
- `..\private\.env` - private values, loaded by `StartJobSearch.exe` into the session environment:
  - `APPLICANT_*` (email, phone, address, LinkedIn/portfolio URLs), `SKIP_COMPANIES`, site usernames, bridge token.
  - `MAIL_CLIENT_ID` - Azure app ID for `mailcheck.py` (read-only Microsoft Graph Mail.Read on the job-application inbox; sign-in cached in `..\private\mail-token.json`). Verification emails / codes (autoApplyLoop step 6e): `python mailcheck.py wait --match <company>,<site> --since <time>` in the background (checks every 2 minutes), then open the link / type the code and continue - Needs User only if it times out or isn't set up (`python mailcheck.py login`).
  - `ANSWER_*` - the **answer bank** for application forms. Each entry has a `# Q: <question>` comment line above it. Read the whole file before every application; only ask the user about questions not covered, then save the new answer with `python applog.py answer ...`.
  Files refer to .env values as `${NAME}`: read .env and substitute the real value when filling a form. Never copy .env values into other files or into applications.json; add new private values to `..\private\.env` (and the empty key to `..\examples\.env.example`) and reference them as `${NAME}`. The only stored password is `APPLICANT_PASSWORD` (job-site accounts, autoApplyLoop step 6b): type it only into a site's password fields - never print, log or copy it.

## Starting the session
There are no timed rounds: the user clicks a search button on the job board, Claude searches in Chrome and adds candidates (step 2g), the user approves jobs into the apply queue, and Claude applies to the queue. When the user says "continue my job search" (or similar) at the start of a session:
1. Read `..\private\job-search-config.json` (all sections), `..\private\.env` (answer bank) and `..\private\applications.json`. Briefly list what `python applog.py open` shows (Needs User / Needs approval / Pending / Candidate) and how many new jobs are waiting on the job board.
2. Start the queue watcher: run `python jobboard.py watch` (in `<repo>\JobSearch`, absolute path on this PC) with the Monitor tool, `timeout_ms` 1800000 (the maximum). It prints a line within ~2 seconds of the user clicking a search button (`search request <id>: ...` -> do a BROWSER SEARCH, autoApplyLoop step 2g) or Add to apply queue (and re-checks every `jobBoard.queueCheckSeconds`, default 30). On each apply-queue line: if a queue run is already in progress, finish it and re-check `python jobboard.py queue` at its end; otherwise do a QUEUE RUN exactly as written in autoApplyLoop step 2q of `<repo>\private\job-search-config.json`, with the ANSWER_* answer bank in `<repo>\private\.env` (re-read both files for every run). A Monitor expires after 30 minutes: re-arm it every time it does, for as long as the session runs.
3. Check right away: if `python jobboard.py searches` lists open search requests, do those searches; if `python jobboard.py queue --quiet` lists jobs, do a queue run.

Browser: Google Chrome, via the tool named in `launcher.browserTool` in the config (`browser-bridge` or `claude-in-chrome`) - for applying to queued jobs (step 2q) and LinkedIn searches the user asks for (step 2b). With `launcher.chromeProfileDir` set (default `private\chrome-job-profile`, gitignored) the launcher opens a **job-only Chrome profile**: its own folder, its own LinkedIn / job-site logins, none of the user's personal accounts; the bridge extension is installed only there (one-time setup shown by the launcher the first time), so Claude never works in the user's personal Chrome. **`apply.autoSubmit`**: true = Claude clicks the final Submit; false (the template default) = Claude fills everything, stops at the last Submit / Send / Apply button, leaves the tab open and logs Needs User "READY TO SUBMIT" (the user submits, then clicks Mark as submitted on the board). Pace LinkedIn per `loop.linkedinSearchDelayMinutes`; stop LinkedIn on HTTP 429.

## Browser bridge
The self-built replacement for Claude in Chrome lives in `..\claude-browser-bridge` (MCP server `browser-bridge` + Chrome extension; token = `BRIDGE_TOKEN` in `..\private\.env`). Setup and startup steps: `..\claude-browser-bridge\START_HERE.md`. If its tools are unavailable, tell the user (check the extension badge) instead of silently switching browsers. Forms inside cross-origin iframes (e.g. iCIMS "Candidate Forms" / self-ID pages) show up in `read_page` under `--- frame f<id>: <url> ---` with refs like `f321-e5`; use them with click / type / select_option / set_checked like any ref (file uploads inside such frames are not supported - open the frame's URL in the tab instead). `upload_file` also works on a "Choose File" / "Upload" button or drop zone with no `<input type=file>` (e.g. Apple Jobs): give the button's ref, the bridge intercepts the file chooser the click opens and fills it - a file picker is not a reason to stop an application. Never interact with captcha frames (hcaptcha / recaptcha). `screenshot` pixels are page coordinates for `click(x, y)`.

## Launcher
`<repo>\StartJobSearch.exe` (source + build script: `..\launcher\`) validates `private\job-search-config.json` and `private\.env`, starts Chrome, starts the job board page in the background (its search buttons ask this Claude session for candidates) and opens it, and opens Claude Code in this folder with a "continue my job search" prompt. If a session already owns the browser bridge port it does not start a second one (only one session can use Chrome).
