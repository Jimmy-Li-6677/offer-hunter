# Job search workspace

`<repo>` = the folder this project is cloned into (the parent of this `JobSearch\` folder). Paths below are relative to this folder.

Layout:
- `JobSearch\` - this folder (Claude's working directory): `CLAUDE.md`, `applog.py`.
- `..\private\` - **all of the user's real data, gitignored**: `.env`, `job-search-config.json`, `resume.json`, the resume PDF, `applications.json`, `applications-archive.md`. A fresh clone has no `private\` yet: copy the files from `..\examples\` (drop `.example` from the names) and fill them in - see `..\README.md`.
- `..\examples\` - public templates of every file in `private\` (`.env.example`, `job-search-config.example.json`, `resume.example.json`, `Resume.example.pdf`, `applications.example.json`, `applications-archive.example.md`). Never put real data, names or personal details here. `job-search-config.example.json` is a generic template, not a copy: sample / `<placeholder>` values for roles, seniority, locations, skip rules, sources; blank `profile`; generic standingRules; the same autoApplyLoop step numbers with the workflow logic only (no names, dates, cities, companies or personal rules). When a workflow step or config field is added or changed in the real config, add the generic version there; when a new `.env` key is added, add it with an empty value to `examples\.env.example`.
- `..\launcher\` (StartJobSearch.exe source), `..\claude-browser-bridge\` (browser MCP server + Chrome extension).
- The repo is public: no names, personal paths (`C:\Users\<username>\...`) or private values in any committed file. Before any git commit / push, show the user the exact file list and wait for their OK.

Files:
- `..\private\job-search-config.json` - loaded by `StartJobSearch.exe`; search requirements and workflow (keep it valid JSON when editing):
  - search requirements: `roles`, `seniority`, `experienceYears`, `postedWithinHours`, `locations`, `minSalary`, `skip`, `sources`, `loop` (LinkedIn pacing), `jobFeed` (job APIs), `jobBoard` (job board: fetch interval, apply queue, watcher), `launcher` settings. Source of truth for WHAT to search; they win over anything conflicting in `profile` / `standingRules`.
  - `profile` - the user's own preference notes; `standingRules` - standing search rules.
  - `autoApplyLoop` - the step-by-step "program" Claude follows (job feed, apply queue, queue runs, forms, logins). New workflow rules from the user go into its `steps`.
- `..\private\applications.json` - log of every submitted / skipped / needs-approval / needs-user / pending / candidate job (older markdown log, if any: `..\private\applications-archive.md`). Use `applog.py`, don't hand-edit:
  - `python applog.py check "<company>" "<role>" [--id <job id>]` before analyzing any job - exit 0 = already logged, skip it.
  - `python applog.py add --company .. --role .. --location .. --status .. --url <job link> [--notes ..] [--id ..]` after each job (updates the existing entry for the same company+role / id). Always record the job link (autoApplyLoop step 1b): the company posting / application page for Submitted (required - applog refuses without it), else the LinkedIn post. `python applog.py list --no-link` shows entries missing a link.
  - `python applog.py open` lists jobs still waiting on the user / approval; `python applog.py note "<text>"` adds a note (e.g. a queue run summary).
  - `python applog.py answer --section <section> --question "<q>" --answer "<a>"` saves a question the user just answered into the ANSWER_* bank in `..\private\.env` (+ empty key in `..\examples\.env.example`); run it right after every new answer (autoApplyLoop step 6d).
- Job search source = `python jobfeed.py` (autoApplyLoop step 2), not LinkedIn browsing (step 2b, only when the user asks). The job board server runs it every `jobBoard.fetchEveryHours` hours and when the user clicks Refresh jobs - Claude does not need to run it. It reads the `jobFeed` section of the config, pulls posts from the company Greenhouse / Lever / Ashby boards in `jobFeed.ats` (no key) and from JSearch / Adzuna (keys `JSEARCH_API_KEY`, `ADZUNA_APP_ID` + `ADZUNA_APP_KEY` in `..\private\.env`; skipped without them), filters by title / location / freshness / skip companies / applications.json, and prints the new candidates with apply links (also saved to `..\private\jobfeed-latest.json`). API request budgets are tracked in `..\private\jobfeed-state.json`. Other options: `--plan` (sources, keys, budget used; no requests), `--rejected` (why jobs were filtered out), `--hours N`, `--source ats|jsearch|adzuna`, `--check-boards` (verify company slugs). When a company keeps showing up with good matches, add its board slug to `jobFeed.ats` (and a generic note to the example config if the field format changes).
- Job board = `python jobboard.py` (autoApplyLoop step 2s): a local page (`http://127.0.0.1:<jobBoard.port>`, default 8766; `jobboard.html`) listing every job `jobfeed.py` found (`..\private\job-board.json`). The user puts jobs in the apply queue (in order) or skips them; with `jobBoard.requireSelection` (default true) Claude applies ONLY to queued jobs. Queued jobs are applied to with a QUEUE RUN (step 2q: one new Chrome tab per job, sign-in via the `wait_for_password` hand-off, blocked jobs logged as Needs User with their tab left open and Claude moving straight on to the next job) started by the queue watcher (see Starting the session) - there are no other apply rounds. `python jobboard.py queue` = the queue in order (exit 1 if empty; `--quiet` = one line for the watcher), `python jobboard.py applying <key>` = mark the job being applied to now; the page shows each job's applications.json status, so log every queued job with `--id <job id>` as usual. Skipped jobs are never shown again by `jobfeed.py` and never applied to. `StartJobSearch.exe` starts the page (`jobBoard.openOnStart`).
- Resume: the PDF in `..\private\` (exact path in autoApplyLoop step 4) is the file to upload; `..\private\resume.json` is the same resume as structured data (jobs, bullets, dates, education, skills) used to fill experience / Role Description fields (autoApplyLoop step 4a). Update both together.
- `..\private\.env` - private values, loaded by `StartJobSearch.exe` into the session environment:
  - `APPLICANT_*` (email, phone, address, LinkedIn/portfolio URLs), `SKIP_COMPANIES`, site usernames, bridge token.
  - `ANSWER_*` - the **answer bank** for application forms. Each entry has a `# Q: <question>` comment line above it. Read the whole file before every application; only ask the user about questions not covered, then save the new answer with `python applog.py answer ...`.
  Files refer to .env values as `${NAME}`: read .env and substitute the real value when filling a form. Never copy .env values into other files or into applications.json; add new private values to `..\private\.env` (and the empty key to `..\examples\.env.example`) and reference them as `${NAME}`. No passwords are stored anywhere.

## Starting the session
There are no timed apply rounds: the job board server fetches jobs (every `jobBoard.fetchEveryHours` hours or on Refresh jobs), the user picks jobs into the apply queue, and Claude applies to the queue. When the user says "continue my job search" (or similar) at the start of a session:
1. Read `..\private\job-search-config.json` (all sections), `..\private\.env` (answer bank) and `..\private\applications.json`. Briefly list what `python applog.py open` shows (Needs User / Needs approval / Pending / Candidate) and how many new jobs are waiting on the job board.
2. Start the queue watcher by invoking the `loop` skill with (`<M>m` = `jobBoard.queueCheckMinutes`, default 10; use the absolute paths of `<repo>\...` on this PC):
   `<M>m Queue watcher: in <repo>\JobSearch run python jobboard.py queue --quiet. If it says "apply queue empty", or a queue run is still in progress, reply only "queue empty" / "busy" and stop. Otherwise do a QUEUE RUN exactly as written in autoApplyLoop step 2q of <repo>\private\job-search-config.json, with the ANSWER_* answer bank in <repo>\private\.env (re-read both files for every run).`
   Choose "This session only" if asked (cloud agents cannot use Chrome).
3. Check the queue right away: if `python jobboard.py queue --quiet` lists jobs, do a queue run now. The watcher lasts until the session ends.

Browser: Google Chrome (the user is signed in to LinkedIn), via the tool named in `launcher.browserTool` in the config (`browser-bridge` or `claude-in-chrome`) - for applying to queued jobs (step 2q) and LinkedIn searches the user asks for (step 2b). Pace LinkedIn per `loop.linkedinSearchDelayMinutes`; stop LinkedIn on HTTP 429.

## Browser bridge
The self-built replacement for Claude in Chrome lives in `..\claude-browser-bridge` (MCP server `browser-bridge` + Chrome extension; token = `BRIDGE_TOKEN` in `..\private\.env`). Setup and startup steps: `..\claude-browser-bridge\START_HERE.md`. If its tools are unavailable, tell the user (check the extension badge) instead of silently switching browsers.

## Launcher
`<repo>\StartJobSearch.exe` (source + build script: `..\launcher\`) validates `private\job-search-config.json` and `private\.env`, starts Chrome, starts the job board page in the background (it fetches jobs every `jobBoard.fetchEveryHours`) and opens it, and opens Claude Code in this folder with a "continue my job search" prompt. If a session already owns the browser bridge port it does not start a second one (only one session can use Chrome).
