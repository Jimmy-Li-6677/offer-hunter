# Job search workspace

`<repo>` = the folder this project is cloned into (the parent of this `JobSearch\` folder). Paths below are relative to this folder.

Layout:
- `JobSearch\` - this folder (Claude's working directory): `CLAUDE.md`, `applog.py`.
- `..\private\` - **all of the user's real data, gitignored**: `.env`, `job-search-config.json`, `resume.json`, the resume PDF, `applications.json`, `applications-archive.md`. A fresh clone has an empty `private\` (only `.gitkeep`, the folder's placeholder; everything else in it is gitignored): copy the files from `..\examples\` (drop `.example` from the names) and fill them in - see `..\README.md`.
- `..\examples\` - public templates of every file in `private\` (`.env.example`, `job-search-config.example.json`, `resume.example.json`, `Resume.example.pdf`, `applications.example.json`, `applications-archive.example.md`). Never put real data, names or personal details here. `job-search-config.example.json` is a generic template, not a copy: sample / `<placeholder>` values for roles, seniority, locations, skip rules, sources; blank `profile`; generic standingRules; the same autoApplyLoop step numbers with the workflow logic only (no names, dates, cities, companies or personal rules). When a workflow step or config field is added or changed in the real config, add the generic version there; when a new `.env` key is added, add it with an empty value to `examples\.env.example`.
- `..\launcher\` (StartJobSearch.exe source), `..\claude-browser-bridge\` (browser MCP server + Chrome extension).
- The repo is public: no names, personal paths (`C:\Users\<username>\...`) or private values in any committed file. Before any git commit / push, show the user the exact file list and wait for their OK.

Files:
- `..\private\job-search-config.json` - loaded by `StartJobSearch.exe`; search requirements and workflow (keep it valid JSON when editing):
  - search requirements: `roles`, `seniority`, `experienceYears`, `postedWithinHours`, `locations`, `minSalary`, `skip`, `sources`, `loop` (LinkedIn pacing), `jobFeed` (job APIs), `jobBoard` (job board: fetch interval, apply queue, watcher), `launcher` settings. Source of truth for WHAT to search; they win over anything conflicting in `profile` / `standingRules`.
  - `profile` - the user's own preference notes; `standingRules` - standing search rules.
  - `autoApplyLoop` - the step-by-step "program" Claude follows (job feed, apply queue, queue runs, forms, logins). New workflow rules from the user go into its `steps`.
- `..\private\applications.json` - log of every submitted / skipped / needs-approval / needs-user / pending / candidate job (older markdown log, if any: `..\private\applications-archive.md`). Use `applog.py`, don't hand-edit:
  - `python applog.py check "<company>" "<role>" [--id <job id>]` before analyzing any job - exit 0 = already logged, skip it.
  - `python applog.py add --company .. --role .. --location .. --status .. --url <job link> [--notes ..] [--id ..]` after each job (updates the existing entry for the same company+role / id). Always record the job link (autoApplyLoop step 1b): the company posting / application page for Submitted (required - applog refuses without it), else the LinkedIn post. `python applog.py list --no-link` shows entries missing a link.
  - `python applog.py open` lists jobs still waiting on the user / approval; `python applog.py note "<text>"` adds a note (e.g. a queue run summary).
  - `python applog.py answer --section <section> --question "<q>" --answer "<a>"` saves a question the user just answered into the ANSWER_* bank in `..\private\.env` (+ empty key in `..\examples\.env.example`); run it right after every new answer (autoApplyLoop step 6d).
- Job search source = Claude's own searches in Chrome (autoApplyLoop step 2g): the job board's **Search Google Jobs** / **Search LinkedIn** buttons save a search request (`..\private\job-board.json`); the watcher prints `search request <id>: google|linkedin`; Claude marks it running (`python jobboard.py search <id> running --note "<query> in all locations"`), searches in a new Chrome tab across EVERY preferred location (each `locations` area + Remote US), busiest first per `browserSearch.locationActivity` (updated after every search), keeps up to `browserSearch.candidatesPerSearch` (10) candidates that pass the search requirements, writes them to a JSON file (company, title, location, workMode, salary, posted, url, applyUrl, description) and adds them with `python jobboard.py add <file.json> --search <id>` (marks the request done; `python jobboard.py search <id> failed --note ..` when blocked). Candidates are NOT logged in applications.json - the user approves them on the board. `python jobboard.py searches [--all]` lists requests. No SerpApi searches are used. The board's **Search SimplifyJobs** button needs no Claude: the board server itself (`simplifyjobs.py`) downloads the SimplifyJobs new-grad list (github.com/SimplifyJobs/New-Grad-Positions, `listings.json`), keeps active software / data / AI jobs that pass `jobfilters.py` and are not on the board yet (widening 12h -> 24h -> 3 days -> 1 week until `browserSearch.candidatesPerSearch`) and adds them as candidates; `python simplifyjobs.py [--dry-run]` does the same from the command line. `python jobfeed.py` (SerpApi Google Jobs, `jobFeed` section, key `SERPAPI_API_KEY`, monthly budget `jobFeed.serpapi.monthlyRequestBudget`) is a manual tool only - run it only when the user asks; its jobs go on the board too (`--plan`, `--search N`, `--rejected`, `--hours N`).
- LinkedIn = the Search LinkedIn button, or when the user asks in chat (autoApplyLoop steps 2g / 2b): same steps, one results page at a time, paced per `loop.linkedinSearchDelayMinutes`, stop on HTTP 429.
- Job board = `python jobboard.py` (autoApplyLoop step 2s): a local page (`http://127.0.0.1:<jobBoard.port>`, default 8766; `jobboard.html`) listing the candidates Claude found (`..\private\job-board.json`) with salary, experience and work mode. The user approves jobs by putting them in the apply queue (in order) or skips them; with `jobBoard.requireSelection` (default true) Claude applies ONLY to queued jobs. Queued jobs are applied to with a QUEUE RUN (step 2q: one new Chrome tab per job, sign-in via the `wait_for_password` hand-off, blocked jobs logged as Needs User with their tab left open and Claude moving straight on to the next job) started by the queue watcher (see Starting the session) - there are no other apply rounds. `python jobboard.py queue` = the queue in order (exit 1 if empty; `--quiet` = one line for the watcher), `python jobboard.py applying <key>` = mark the job being applied to now; the page shows each job's applications.json status, so log every queued job with `--id <job id>` as usual. Skipped jobs are never applied to (and not offered again). Jobs under "Waiting on you" (Needs User / Needs approval / Pending / Candidate) have **Continue application** (Needs User: puts the job back at the END of the apply queue, no page is opened - `python jobboard.py queue` marks it CONTINUE, finish it where it stopped), **Mark as submitted** (the user finished it themselves -> Submitted), **Skip** (-> Skipped) and, for Needs approval / Pending / Candidate, **Approve & apply** (-> status Approved and back in the apply queue; `python jobboard.py queue` marks it APPROVED BY THE USER - apply even though it failed a rule). The page has Location (the `locations` areas, Any location, Other) and Salary (Any salary, Salary listed, $50K+ ... $200K+) dropdowns and a "Hide jobs that fail a filter" checkbox per search filter - the filters (jobFeed regexes, `experienceYears`, `skip.rules`, `jobFeed.staffingAgencies`) live in `jobfilters.py`, shared with `jobfeed.py`; each card lists the filters it fails. These choices are saved in the browser only; Claude still applies to exactly what is in the queue. **Update my answers** (autoApplyLoop step 2u): the user uploads a resume (`..\private\uploads\`; the watcher prints `profile request <id>: new resume <path>` -> read it, update `resume.json`, fill answers with `python answerbank.py set KEY "value"`, then `python jobboard.py profile done --note ..`) and fills in the rest of the questions on a form (`answerbank.py`: APPLICANT_* / ANSWER_* values plus common questions not in the bank; `python answerbank.py missing` lists blanks; secrets are never shown). `StartJobSearch.exe` starts the page (`jobBoard.openOnStart`).
- Resume: the PDF in `..\private\` (exact path in autoApplyLoop step 4) is the file to upload; `..\private\resume.json` is the same resume as structured data (jobs, bullets, dates, education, skills) used to fill experience / Role Description fields (autoApplyLoop step 4a). Update both together.
- `..\private\.env` - private values, loaded by `StartJobSearch.exe` into the session environment:
  - `APPLICANT_*` (email, phone, address, LinkedIn/portfolio URLs), `SKIP_COMPANIES`, site usernames, bridge token.
  - `ANSWER_*` - the **answer bank** for application forms. Each entry has a `# Q: <question>` comment line above it. Read the whole file before every application; only ask the user about questions not covered, then save the new answer with `python applog.py answer ...`.
  Files refer to .env values as `${NAME}`: read .env and substitute the real value when filling a form. Never copy .env values into other files or into applications.json; add new private values to `..\private\.env` (and the empty key to `..\examples\.env.example`) and reference them as `${NAME}`. The only stored password is `APPLICANT_PASSWORD` (job-site accounts, autoApplyLoop step 6b): type it only into a site's password fields - never print, log or copy it.

## Starting the session
There are no timed rounds: the user clicks a search button on the job board, Claude searches in Chrome and adds candidates (step 2g), the user approves jobs into the apply queue, and Claude applies to the queue. When the user says "continue my job search" (or similar) at the start of a session:
1. Read `..\private\job-search-config.json` (all sections), `..\private\.env` (answer bank) and `..\private\applications.json`. Briefly list what `python applog.py open` shows (Needs User / Needs approval / Pending / Candidate) and how many new jobs are waiting on the job board.
2. Start the queue watcher: run `python jobboard.py watch` (in `<repo>\JobSearch`, absolute path on this PC) with the Monitor tool, `timeout_ms` 1800000 (the maximum). It prints a line within ~2 seconds of the user clicking a search button (`search request <id>: ...` -> do a BROWSER SEARCH, autoApplyLoop step 2g) or Add to apply queue (and re-checks every `jobBoard.queueCheckSeconds`, default 30). On each apply-queue line: if a queue run is already in progress, finish it and re-check `python jobboard.py queue` at its end; otherwise do a QUEUE RUN exactly as written in autoApplyLoop step 2q of `<repo>\private\job-search-config.json`, with the ANSWER_* answer bank in `<repo>\private\.env` (re-read both files for every run). A Monitor expires after 30 minutes: re-arm it every time it does, for as long as the session runs.
3. Check right away: if `python jobboard.py searches` lists open search requests, do those searches; if `python jobboard.py queue --quiet` lists jobs, do a queue run.

Browser: Google Chrome (the user is signed in to LinkedIn), via the tool named in `launcher.browserTool` in the config (`browser-bridge` or `claude-in-chrome`) - for applying to queued jobs (step 2q) and LinkedIn searches the user asks for (step 2b). Pace LinkedIn per `loop.linkedinSearchDelayMinutes`; stop LinkedIn on HTTP 429.

## Browser bridge
The self-built replacement for Claude in Chrome lives in `..\claude-browser-bridge` (MCP server `browser-bridge` + Chrome extension; token = `BRIDGE_TOKEN` in `..\private\.env`). Setup and startup steps: `..\claude-browser-bridge\START_HERE.md`. If its tools are unavailable, tell the user (check the extension badge) instead of silently switching browsers.

## Launcher
`<repo>\StartJobSearch.exe` (source + build script: `..\launcher\`) validates `private\job-search-config.json` and `private\.env`, starts Chrome, starts the job board page in the background (its search buttons ask this Claude session for candidates) and opens it, and opens Claude Code in this folder with a "continue my job search" prompt. If a session already owns the browser bridge port it does not start a second one (only one session can use Chrome).
